# 작업 지시서: /recommend 추천 로직 개선 (리뷰 호평률 블렌딩 + 코사인 정규화)

## 배경 및 목적

PlayDate(`pick.py`)의 "Pick 6" 추천을 검토한 결과, 현재 우리 `/recommend`가 취하지
않는 두 가지 개선점을 확인했다.

1. **리뷰 호평률 미반영** — 본 서비스는 *리뷰 피드* 앱이라 리뷰 데이터를 이미
   다루는데, 정작 추천 랭킹은 장르·카테고리 매칭만 쓴다. 취향은 맞지만 평이 나쁜
   게임이 상위에 올라올 수 있다. PlayDate처럼 호평률을 점수에 블렌딩하면
   "내 취향 + 평 좋은 게임" 순으로 품질이 오른다.
2. **다태그 편향** — `scoreAgainstProfile`이 매칭된 share를 단순 합산하므로,
   장르·카테고리가 많이 달린 게임이 구조적으로 유리하다. 후보 벡터의 크기(norm)로
   나누는 **코사인 유사도**로 이 편향을 제거한다.

두 개선은 독립적이며 난이도·리스크가 크게 다르다. **#2(코사인)는 `profile.ts`
순수 함수 내부 변경으로 I/O·비용 0**, **#1(리뷰 블렌딩)은 추가 Steam API 호출과
라우트 2단계화가 필요**하다. 따라서 단계를 분리하여 #2를 먼저, #1을 뒤에 둔다.

## 현재 상태

### 매칭 점수 (`lib/steam/profile.ts:349-376`)
```
score = Σ(matchedGenre.share) + W_CAT · Σ(matchedCategory.share)   // W_CAT=0.3
```
- share 는 프로필 차원 내 정규화 비율(컷 후 합=1.0).
- 후보의 태그 수가 많을수록 매칭 항이 많아져 점수가 누적 상승 → **다태그 편향**.
- score ≤ 0 이면 후보 탈락. 정렬: score desc → (playtime desc | priority asc) → appid asc.

### 리뷰 점수 데이터 가용성 (중요 제약)
- 호평률(`review_score` 0~10, `total_positive`, `total_negative`, `total_reviews`)은
  `appreviews` 엔드포인트의 `query_summary`에서 온다 (`lib/steam/types.ts:194-205`).
- **현재 `getReviews`(`lib/steam/api.ts:424-459`)는 `query_summary`를 버리고
  `res.reviews` 배열만 반환한다.** 요약 점수를 얻는 함수가 없다.
- 추천 플로우(`app/api/recommend/route.ts`)는 `getAppDetailsBatch`만 호출한다.
  `appdetails`에는 리뷰 점수가 **없다**. → 리뷰 블렌딩은 **추가 per-후보 API 호출** 필수.
- Rate Limit: `STEAM_API_DELAY.reviews = 500ms`, `STREAM_CONCURRENCY = 1` (직렬).
  → 후보 N개당 최소 0.5N초. 전체 라이브러리(수천 개)에 절대 걸면 안 되고,
  **매칭 점수로 선별한 shortlist에만** 걸어야 한다.

### 순수성 계약
`profile.ts` 모듈 헤더(`:1-6`)는 "외부 의존 없는 순수 함수만 노출, I/O·캐시 접근은
호출 측 책임"을 명시한다. 리뷰 fetch는 이 계약을 깨면 안 된다 → **리뷰 점수는
데이터로 주입**받고, 블렌딩 산식만 순수 함수로 둔다.

## 변경 계획

### 단계 1 — 코사인 정규화 (`profile.ts` 순수 변경, I/O 없음)

**대상: `scoreAgainstProfile` (`lib/steam/profile.ts:349-376`)**

**진짜 코사인 유사도**를 적용한다 (Momus C1/C2/C-NEW 반영 — dot/norm 벡터공간 일관).
두 벡터를 **하나의 내적 공간**에서 명시적으로 정의한다. 핵심: `W_CAT`는 **프로필 벡터
쪽에만** 얹고, 후보 벡터는 순수 이진(1)으로 둔다. 이렇게 해야 dot이 기존 `matchRaw`와
같아지면서 dot·‖a‖·‖b‖가 동일 공간에서 일관된다.

- 프로필 벡터 **a**: 장르 차원 = `share`, 카테고리 차원 = `W_CAT·share`, 미보유 = 0.
  (분석 1회당 **고정 상수 벡터**)
- 후보 벡터 **b**: 후보 보유 장르 차원 = 1, 카테고리 차원 = 1, 미보유 = 0 (순수 이진).

```
dot   = a·b = Σ(matchedGenre.share) + W_CAT · Σ(matchedCategory.share)   // = 기존 matchRaw
‖a‖   = sqrt( Σ_genre(share²) + W_CAT² · Σ_cat(share²) )   // 프로필 norm, 분석당 1회·상수
‖b‖   = sqrt( genreIds.length + categoryIds.length )        // 후보 norm = √(전체 태그 수)
matchScore = (‖a‖>0 && ‖b‖>0) ? dot / (‖a‖ · ‖b‖) : 0
```

- **일관성 검산 (C-NEW)**: 카테고리 매칭 차원의 성분곱 = `(W_CAT·share)·1 = W_CAT·share`
  → dot의 카테고리 항은 `W_CAT¹`(matchRaw와 동일). `‖b‖`는 후보가 이진(1)이므로
  `√(태그 수)`, **W_CAT² 없음**. `‖a‖`만 프로필 성분(`W_CAT·share`)의 제곱이라 `W_CAT²`.
  세 값이 모두 같은 벡터(a: share/W_CAT·share, b: 1/1)에서 나오므로 Cauchy-Schwarz
  `dot ≤ ‖a‖·‖b‖`가 성립 → **matchScore ∈ [0,1] 엄밀 보장**.
  - 검산 예(W_CAT=0.3, 프로필=카테고리 1개 share=1.0, 후보가 그 카테고리 보유):
    dot=0.3, ‖a‖=√(0.3²·1²)=0.3, ‖b‖=√1=1 → matchScore=0.3/(0.3·1)=**1.0** ✓
- **왜 프로필 norm 포함인가 (C2)**: `‖a‖`(상수)는 순위엔 무영향이나, 단계 2에서
  reviewScore([0,1])와 블렌딩하려면 matchScore도 **[0,1] 유계**여야 한다. `‖a‖`로
  나누면 shortlist-상대 max 정규화(런마다 max가 바뀌어 순위 불안정) 없이 **런 독립·
  결정론적** [0,1]이 확정된다. → 스케일 불일치 원천 제거.
- **매칭 0개 후보 탈락 유지** — dot=0 → matchScore=0. 기존 `score<=0` 규칙 불변.
- **엣지**: `‖a‖=0`(analyzedGames=0 등)이면 모든 matchScore=0 → 빈 추천(기존과 동일).

**Recommendation 타입 (`:167-180`)**
- `score` 필드의 의미를 "최종 순위 점수"로 유지하되, 단계 1에서는 `score = matchScore`.
- 단계 2 대비 필드 추가: `matchScore: number` (취향 매칭 정규화 점수),
  `reviewScore?: number` (0~1, 단계 2에서 채움), `score`(최종 블렌딩 결과).
  단계 1에서는 `matchScore`만 채우고 `score = matchScore`, `reviewScore` 미정의.

**정렬 (`recommendLibraryUnplayed:416-423`, `recommendFromWishlist:462-471`)**
- `score`(=matchScore) desc 기준 유지. 동률 tie-break 규칙 불변.

**테스트**: `__tests__/profile.test.ts` (현재 29개 `it` 케이스)
- 매칭 점수 절대값을 단언하는 케이스는 코사인 값으로 갱신.
- **순위 변화의 성격 (C-NEW 명확화)**: `‖a‖`(상수) 포함은 순위 불변(양의 상수배).
  `‖b‖`(후보 norm) 정규화는 **의도된 순위 변화** — 다태그 후보가 낮아진다. 따라서
  "순위 회귀 없음"이 아니라 "다태그 편향만큼 순위가 바뀌고 그 방향이 옳음"을 검증한다.
- **신규 결정론 케이스 A — 다태그 편향 제거 (장르만)**:
  - 프로필: 장르 G1 share=0.6, G2 share=0.4.
  - 후보 X: genreIds=[G1,G2]. 후보 Y: genreIds=[G1,G2,N1,N2,N3,N4] (N*는 프로필 밖).
  - dot 동일(1.0). ‖b_X‖=√2, ‖b_Y‖=√6 → matchScore_X > matchScore_Y.
    **동일 매칭인데 태그만 많은 Y가 패널티**를 단언.
- **신규 결정론 케이스 B — [0,1] 유계 (카테고리 포함, C-NEW 회귀)**:
  - 프로필: 카테고리 C1 share=1.0 (장르 없음). 후보 Z: categoryIds=[C1].
  - 기대: dot=W_CAT, ‖a‖=W_CAT, ‖b‖=1 → **matchScore=1.0 정확히**.
    (카테고리 편중 프로필에서 matchScore가 1을 초과하지 않음을 못박음 — dot의
    W_CAT¹ vs norm의 W_CAT² 불일치 버그가 재발하면 이 케이스가 3.33로 실패한다.)
  - 혼합 케이스: 장르+카테고리 동시 매칭 후보의 matchScore ≤ 1.0 도 단언.

### 단계 2 — 리뷰 호평률 블렌딩

#### 2-1. 리뷰 요약 조회 API (`lib/steam/api.ts`)
신규 `getReviewSummary(appId): Promise<ReviewSummary | null>`:
- `appreviews/{appId}?json=1&num_per_page=0&language=all&purchase_type=all&filter=all` 호출.
  - `filter=all` — 전체 기간 누적 `total_positive/total_negative/total_reviews`를 받기 위함
    (`getReviews`의 `filter=recent`는 롤링 요약이라 부적합).
  - `num_per_page=0` — 본문 리뷰 불필요, 페이로드 최소화. 응답에 `reviews`가 비어도
    `query_summary`는 채워짐. **단 M3: `num_per_page=0` 미지원 가능성 대비 —
    Steam이 빈 요약을 주면 `total_reviews=0`로 처리(fallback으로 자연 흡수).**
- **반환 계약 (M3/M4)**: `res` 없음 또는 `res.success !== 1` → `null`
  (`getReviews:454` 패턴 동일). 성공 시 `query_summary` 전체를 담은
  `ReviewSummary = { reviewScore, reviewScoreDesc, totalPositive, totalNegative, totalReviews }`
  반환 — `review_score`(0~10)·`review_score_desc`도 보존해 향후 UI 배지(2-6)에서 재사용.
- **캐시 (M1 — v1은 인메모리만)**: 별도 키 `reviewsummary:{appId}` + 신규 상수
  `CACHE_TTL.reviewSummary`(`lib/cache.ts:34-45`에 추가, 리뷰 요약은 느리게 변하므로
  `reviews`보다 김, 예: 6h). `getReviews`의 `reviews:*` 키와 분리. **영속(SQLite)
  캐시는 범위 밖** — 필요 시 `app-details-store.ts` + `db.ts`의 `app_details_cache`
  테이블 패턴을 미러링하는 후속 작업으로 분리(신규 `review_summary_cache` 테이블 DDL).
- `STEAM_API_DELAY.reviews`(500ms) 딜레이 준수.

`ReviewSummary` 타입은 `lib/steam/types.ts`에 추가.

#### 2-2. 호평률 정규화 산식 (`profile.ts` 순수 함수)
Steam `review_score`(0~10 등급)는 표본 수를 반영 못 한다. **Wilson 하한** 또는
**호평 비율 + 표본 가중**을 쓴다. 1차는 단순·설명가능성 우선:

```
positiveRatio = totalReviews > 0 ? totalPositive / totalReviews : fallback   // fallback=0.5
// 표본이 적으면 신뢰도 낮음 → 0.5(중립)로 수축
confidence   = min(totalReviews, 50) / 50        // 50개 이상이면 완전 신뢰
reviewScore  = 0.5 + (positiveRatio - 0.5) · confidence   // [0,1]
```
- 표본 부족·요약 없음 → `reviewScore = 0.5`(중립, PlayDate의 tags fallback과 동일 철학).
- 이 산식은 `blendReviewScore()` 같은 **순수 함수**로 `profile.ts`에 두고 단위 테스트.

#### 2-3. 블렌딩 (`profile.ts` 순수 함수)
PlayDate 기본 가중 `0.65·tags + 0.35·review` 채택:
```
finalScore = W_MATCH · matchScore + W_REVIEW · reviewScore   // W_MATCH=0.65, W_REVIEW=0.35
```
- **스케일 일치 (C2 해결)**: 단계 1에서 matchScore는 진짜 코사인으로 **[0,1] 유계·런
  독립**, reviewScore도 [0,1]. 두 항 모두 결정론적 [0,1]이므로 **shortlist-상대 max
  정규화 불필요** — 순위 불안정 원인 제거. 별도 재스케일 없이 그대로 가중 합.
- 상수 `W_MATCH`, `W_REVIEW` (합=1) 를 export 하여 조정 가능.
- **블렌딩은 shortlist 재랭킹 단계에서만** 적용 (아래 2-4).
- tie-break: finalScore desc → matchScore desc → (playtime desc | priority asc) →
  appid asc. 부동소수 동률 시 appid로 최종 결정론 보장.

#### 2-4. 라우트 2단계화 (`app/api/recommend/route.ts`)
`computeRecommendations`(`:174-187`)가 반환하는 match-only 추천을 받아,
**최종 result 단계에서만** 리뷰 블렌딩을 수행:

1. 각 트랙에서 matchScore 기준 상위 **shortlist**(`min(maxPerTrack·2, 30)`개)를 뽑는다.
   후보가 shortlist 크기보다 적으면 **있는 만큼만**(전부) 대상. → 리뷰 fetch 상한을
   강하게 제한.
2. **두 트랙 shortlist의 appid를 합쳐 중복 제거(M2)** 후 한 번에 `getReviewSummary` 조회
   (라이브러리/위시리스트는 route.ts:372에서 이미 배타적이라 실무상 겹치지 않지만,
   안전하게 dedupe하여 fetch·캐시 중복 방지). 최악 상한 = 30+30 = 60 fetch × 500ms
   ≈ 30초(캐시 미스 전량 시). 캐시 히트 시 대폭 단축.
3. `getAppDetailsBatch`와 동일한 취소·직렬 패턴으로 조회. 진행률은 신규 progress
   phase(`fetching-reviews`)로 emit. 배치 전 `isCancelled` 검사.
4. 조회 결과(appid→ReviewSummary)로 각 트랙에서 `blendReviewScore`+블렌딩 재랭킹,
   상위 `maxPerTrack`로 truncate.
5. `reviewScore`·`totalReviews`·최종 `score`를 Recommendation에 채워 `result`/캐시에 반영.

- **partial-result 는 match-only 유지** — 스트리밍 중 리뷰 fetch는 비용 과다.
  중간 결과는 취향 매칭 순위로 보여주고, 최종에서만 리뷰 블렌딩으로 확정.
  (문서 주석으로 이 의도를 명기)
- `tracks`에서 해당 트랙이 꺼져 있으면 리뷰 fetch skip.
- 리뷰 fetch 실패한 후보는 `reviewScore=0.5`로 진행(추천에서 탈락시키지 않음).

#### 2-5. 캐시 payload / 시그니처 영향
- `RecommendationCachePayload`(`lib/recommend-cache.ts:25-30`)는 `Recommendation[]`을
  그대로 저장하므로 **필드 추가는 하위 호환**(기존 캐시 읽을 때 신규 필드 undefined).
- `computeResultSignature`(`route.ts:242-252`)는 appid만 sig에 넣는다. 리뷰 블렌딩으로
  **순위(appid 집합·순서)가 바뀌면 sig가 달라져** 정상적으로 갱신된다. 별도 수정 불필요.
- 단, 리뷰 블렌딩은 final에만 적용되므로 partial→final 사이 순위가 바뀔 수 있다.
  final write는 이미 `force=true`(`route.ts:474`)라 반드시 갱신됨 — 문제 없음.

#### 2-6. UI (`app/recommend/`)
- 추천 카드에 호평률 배지(선택) 표시. 데이터가 `reviewScore`/`totalReviews`로 내려가면
  프론트에서 렌더. **본 지시서 범위 밖(선택)** — 백엔드 데이터 노출까지만 필수,
  UI 배지는 후속.

## 제약 조건

- **하위 호환**: `Recommendation`·캐시 payload에 **필드 추가만**, 기존 필드 제거·의미
  변경 금지. 기존 캐시 row는 신규 필드 없이도 유효해야 함.
- **순수성**: `profile.ts`는 I/O 무의존 유지. 리뷰 데이터는 인자로 주입.
- **API 비용**: 리뷰 fetch는 shortlist(트랙당 상한, 총 ≤ 60)로 제한. 전체 라이브러리
  대상 절대 금지. 요약은 인메모리 캐싱(v1; 영속은 후속, 2-1 참조).
- **취소 안전**: 리뷰 fetch 루프도 기존 `isCancelled` 패턴 준수(배치 전 검사).
- **결정론**: 모든 정렬 tie-break에 appid asc 최종 기준 유지. 부동소수 동률 시 순위
  흔들림 방지.
