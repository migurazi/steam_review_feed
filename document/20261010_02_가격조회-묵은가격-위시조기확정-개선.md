## 배경 및 목적

20261010_01 단계 1에서 가격 조회 경로를 신설했다(`getAppPricesBatch`, `getAppPrice` 재작성). 이전에는 만료된 가격을 영원히
"신선"하게 돌려주는 결함이 있었는데, 고치는 과정에서 반대 방향의 문제가 생겼다.

1. **일시 장애가 가격 소실로 번진다.** 만료 가격의 fallback이 만료당 한 번만 가능하다(#1, #2).
2. **게임 상세 가격 응답이 느려졌다.** 단건 대화형 요청도 배치용 딜레이(1.5초)와 공유 backoff(최대 30초)를 기다린다(#5).
3. **같은 게임의 가격 조회가 중복된다.** 동시 요청 dedupe가 없다(#6).
4. **/recommend 위시 트랙이 시드 성향으로 굳는다.** 대형 라이브러리의 phase B(수 분~수십 분) 내내 갱신되지 않는다(#3).
5. **스트리밍 경로의 중복 계산.** partial마다 버려지는 위시 전체 정렬, 조기 단계의 `analyzeTaste` 2회(#9).

목표: 장애 시에도 "마지막으로 확인한 가격"을 정직하게(회색·시각 표시) 계속 보여주고, 상세 화면 응답을 즉시로 되돌리며,
위시 트랙이 성향 정밀화를 따라가게 한다.

**비목표**
- 리뷰 피드(`/api/reviews/stream`)가 info LRU의 7일 묵은 `price_overview`를 읽는 문제 — 20261010_01 비목표 그대로 유지.
- 가격 데이터의 영속(SQLite) 저장 — 가격은 짧은 수명이라 인메모리로 충분(단, 아래 1-1의 last-known은 인메모리).

## 현재 상태

### lru-cache allowStale 동작 (`lib/cache.ts:22-28`, v11)
- `allowStale: true` + `noDeleteOnStaleGet` 미설정 → **만료 항목을 처음 `get`할 때 값을 돌려주면서 삭제**한다.
- `cacheGet`은 이 값을 `isStale: true`로 반환한다(`lib/cache.ts:80-100`). 즉 stale 값은 **정확히 한 번** 읽힌다.

### `getAppPrice` (`lib/steam/api.ts:441-456`, 단계 1 재작성)
```
fresh 캐시   → 반환
stale 캐시   → stale 반환 + 백그라운드 getAppPricesBatch([appId])
미스         → await getAppPricesBatch([appId])  (1.5s delay + backoff)
```
- **#1**: stale 첫 읽기에서 항목이 삭제된다. 백그라운드 재조회가 429 등으로 실패하면 아무것도 다시 캐시되지 않는다.
  두 번째 요청은 완전 미스 → 1.5초 + backoff(최대 30초) 대기 후 실패 → `null`. 상세 화면 가격이 사라진다.
  (커밋된 이전 구현은 `cached`가 있으면 무조건 반환해 이 문제가 없었다. 대신 만료 가격을 영원히 신선하게 보여주는 결함이 있었다.)
- **#6**: 진행 중 요청 dedupe가 없다. 만료 직후 여러 탭·사용자가 같은 게임을 열면 각자 store 호출을 하고, 그 429가
  /recommend가 의존하는 공유 backoff를 올린다.

### `getAppPricesBatch` stale fallback (`lib/steam/api.ts:550-557`)
- **#2**: 재조회 실패 시 stale 스냅샷(24시간 이내)을 결과에 넣지만 **캐시에 다시 쓰지 않는다**. 1분 뒤 두 번째 분석에서는
  캐시가 비어 커버리지 < `PRICE_COVERAGE_MIN`(0.5) → `priceFetchFailed=true` → 가성비 블렌딩 off, saleOnly면 위시 트랙이
  "가격 실패" 안내로 비워진다. 일시적 Rate Limit 하나가 연속 분석의 결과를 바꾼다.

### 게임 상세 가격 라우트 (`app/api/game/[appId]/price/route.ts:27-36`)
- **#5**: info 캐시(7일)는 히트, 가격 캐시(1시간)는 미스인 경우가 가장 흔하다(방문 1시간 후 대부분). 이 경로가 이제
  `getAppPricesBatch`를 기다려 **최소 1.5초, /recommend가 backoff를 올린 동안 최대 ~31.5초**가 걸린다.
  커밋된 이전 구현은 `getAppDetails`가 info LRU의 `price_overview`(최대 7일 묵음)를 즉시 반환해 0초였다.

### /recommend 위시 조기 확정 (`app/api/recommend/route.ts`, "3b. 조기 위시 단계")
- phase A(시드 20개 + 위시리스트 메타) 직후 시드 성향으로 위시 트랙을 가격·리뷰까지 블렌딩해 `earlyWishlist`로 확정한다.
- phase B의 모든 partial-result는 `earlyWishlist`를 **그대로** 보낸다(`makeMetaProgress` 내 `partialTracks`, `wishlistRecs` 계산).
- **#3**: 시드 게임 메타가 부족(Rate Limit 등)하거나 시드 성향이 편향되면 `earlyWishlist`가 비거나 엉뚱한 목록이 되고,
  phase B 전체(수천 게임 × 1.5초) 동안 고쳐지지 않는다. 최종 result에서만 전체 성향으로 재계산된다.
  단계 1 이전에는 3초마다 매칭 전용 위시 목록이 갱신됐다.
- **심각도 상향 (2026-10-10)**: 메타 조회 순서가 `orderMetaFetch`(phase A = 캐시분, phase B = 미캐시 후보 → 나머지·위시 번갈아)로
  바뀌어, 미캐시 위시 게임은 이제 phase B에서 도착한다. 대형 위시리스트(실사용자 3,736개 중 대부분 미캐시)면 조기 확정 목록은
  캐시된 일부 위시만으로 만들어지고, 나머지 수천 개는 수 시간짜리 phase B가 끝나는 최종 result에서야 반영된다.
  3-1(주기 재블렌딩)의 우선순위를 높인다.

### 중복 계산 (`route.ts` `computeRecommendations`)
- **#9**: 위시 트랙은 항상 `recommendFromWishlist(..., Number.MAX_SAFE_INTEGER)`로 전체를 정렬한 뒤 slice한다. `wishlistAll`은
  `planWishlist`(최종·조기 단계)만 쓰므로 partial(3초마다)에서는 버려진다. 조기 단계는 `computeRecommendations`를 두 번
  호출(위시용 + 라이브러리용)해 `analyzeTaste`가 라이브러리 전체에 대해 2회 돈다.
  비용은 수천 게임 규모에서 수 ms~수십 ms 수준이라 체감 영향은 작다 — 우선순위 낮음.

## 변경 계획

### 1. 가격 캐시 — last-known 가격 분리 (#1, #2)

**1-1. last-known 키 신설** (`lib/steam/api.ts`)
- 가격을 성공적으로 받을 때마다 기존 `app:{id}:price:KR`(TTL `appPrice`=1h)에 더해
  `app:{id}:price:last:KR`에 `{ price, fetchedAt }`를 TTL `PRICE_LAST_KNOWN_TTL_MS`(24h)로 저장한다.
  `getAppDetails` 신규 조회 경로(`api.ts:411` 부근)도 같은 헬퍼로 저장한다.
- 신선도 판단은 기존 키, **장애 fallback은 last-known**으로 역할을 나눈다. last-known은 만료 전까지 여러 번 읽혀도 남는다
  (24h TTL 안에서는 stale이 아니므로 삭제되지 않음).
- 헬퍼: `writePriceCache(id, price, ttl, fetchedAt)` / `readLastKnownPrice(id): PriceSnapshot | null`.
- 대안 검토: `noDeleteOnStaleGet: true`를 전역 설정 — 다른 모든 캐시 키의 의미가 바뀌어 기각.

**1-2. `getAppPricesBatch`**
- 재조회 실패분은 `staleById` 대신 `readLastKnownPrice`로 채운다(원래 `fetchedAt` 유지 → 클라이언트 회색 표시).
  `PRICE_STALE_FALLBACK_MAX_AGE_MS`(24h) 상수는 last-known TTL로 대체하고 제거.
- 첫 읽기에서 stale을 보관하던 `staleById` 로직 제거(단순화).

**1-3. `getAppPrice`**
```
fresh                 → 반환
그 외(stale·미스)      → last-known이 있으면 즉시 반환 + 백그라운드 재조회(dedupe)
last-known도 없음      → 재조회 대기 (아래 2의 대화형 경로)
```
- 반환 타입은 `SteamPriceOverview | null` 유지(라우트 응답 형식 불변). 묵은 가격 표시가 필요하면 2-2에서 `fetchedAt` 노출.

### 2. 게임 상세 가격 응답 (#5, #6)

**2-1. in-flight dedupe**
- 모듈 스코프 `Map<number, Promise<PriceSnapshot | undefined>>`. 같은 appid 재조회가 진행 중이면 그 Promise를 공유.
  완료 시(성공·실패 모두) 맵에서 제거. `getAppPricesBatch`의 배치 조회와는 별개(배치는 이미 appid를 dedupe함).

**2-2. 대화형 단건 경로**
- `getAppPrice`의 미스 경로는 **base delay(1.5s)를 생략**하고 공유 backoff만 따른다. 근거: 사용자 클릭당 1회 호출이라
  배치처럼 연속 호출하지 않는다. backoff가 0이 아니면(최근 429) 대기 대신 **last-known 또는 info LRU의 `price_overview`를
  즉시 반환**하고 백그라운드로 재조회한다.
  - info LRU 가격은 최대 7일 묵을 수 있으므로 반환 시 `fetchedAt`(= info 캐시 `fetchedAt`)을 함께 낸다.
- 라우트 응답에 `priceFetchedAt?: number`를 추가(필드 추가만, 하위 호환). `components/GamePrice.tsx`의 `stale` prop을
  상세 화면에서도 `PRICE_STALE_MS` 기준으로 켠다 — 묵은 가격 시각 구분(정직성 제약).
- 단계 1 주석의 "가격보다 info를 먼저 조회" 순서는 유지(info 신규 조회가 가격 캐시도 채움).

### 3. /recommend 위시 트랙 갱신 (#3)

**3-1. phase B 중 주기적 재블렌딩**
- `earlyWishlist`를 "고정"에서 "주기 갱신"으로 바꾼다. partial throttle(3초)과 별도로 `EARLY_WISH_REFRESH_MS`(예: 30초)마다:
  1. 현재 merged detailsMap으로 위시 shortlist 재계산(`computeRecommendations(..., { lib: false, wish: true }, shortlistSize, priceMap)`).
  2. 새 shortlist 중 **리뷰 요약 캐시가 없는 appid만** `getReviewSummary`로 조회. 한 번 갱신당 상한 `EARLY_WISH_REVIEW_CAP`(예: 5).
     appreviews는 store backoff를 공유하지 않지만, 이 조회는 phase B 메타 조회와 같은 스트림에서 직렬로 기다리므로(0.5초 × N)
     상한으로 phase B 지연을 묶는다. 상한을 넘은 후보는 중립 0.5로 블렌딩하고 다음 갱신에서 채운다.
  3. `blendWishlistTrack` → 배지 부착 → `earlyWishlist` 교체.
- 가격(`priceMap`)은 조기 단계에서 받은 것을 재사용(1시간 TTL 내).
- 시드 성향 품질이 낮을 때(예: `profile.genres.length === 0`) 조기 확정 자체를 건너뛰고 기존 매칭 전용 partial로 두는 가드 추가.
- signature: 위시 목록이 바뀌면 partial이 다시 emit되도록 기존 `computeResultSignature`가 이미 appid·할인율을 포함 — 변경 불필요.

**3-2. 대안 (검토 후 택1)**
- (a) 위 3-1(주기 재블렌딩) — 권장. 리뷰 조회가 점진적이라 비용 통제가 쉬움.
- (b) partial마다 매칭 전용 위시 목록에 `earlyWishlist`의 가격·배지만 덧입혀 보냄 — 구현은 단순하나 saleOnly·가성비 순위가 partial마다
  매칭 순위로 바뀌어 깜빡인다(단계 1이 조기 확정을 도입한 이유).

### 4. 중복 계산 제거 (#9, 낮은 우선순위)
- `computeRecommendations`에 `needWishlistAll: boolean` 인자 추가. false면 `recommendFromWishlist(..., limit)`로 바로 자르고
  `wishlistAll`은 빈 배열(또는 undefined). partial 경로는 false, `planWishlist`를 쓰는 경로만 true.
- 조기 단계의 두 번 호출을 `{ lib: tracks.lib, wish: true }` 한 번으로 합쳐 `analyzeTaste` 1회.
- 결과는 비트 단위로 동일해야 한다(정렬 키 불변) — 회귀 테스트로 고정.

## 제약 조건

- **하위 호환**: `/api/game/[appId]/price` 응답은 필드 추가만. `getAppPrice` 반환 타입 불변.
- **Rate Limit**: 배치 경로(`getAppPricesBatch`)는 base delay + backoff 유지. 대화형 단건만 base delay 생략, backoff가 있으면 대기하지 않고
  캐시값 반환. 신규 동시성 금지(dedupe로 오히려 감소).
- **정직성**: 묵은 가격은 항상 `fetchedAt`과 함께 내려 회색·"N시간 전 가격"으로 구분. 가격 미상을 "할인 없음"으로 표시하지 않음.
- **결정론**: 위시 재블렌딩의 정렬 tie-break 불변.
- 이모지 금지, `node_modules/next/dist/docs/` 확인(AGENTS.md).

### 지시서와 달라진 점
1. **커버리지 판정에서 fallback 제외**: 조회 실패분을 채운 last-known은 `fallback: true`로 표시하고, 위시 가격 커버리지(`PRICE_COVERAGE_MIN`)에는
   이번에 실제로 확인한 가격만 센다. 장애 중 묵은 할인율이 가성비 순위·saleOnly를 조용히 바꾸지 않게 하기 위함(카드에는 회색으로 표시).
2. **backoff 중 info LRU 가격도 24시간 상한**: info는 7일 캐시라 그대로 쓰면 끝난 할인이 보일 수 있다. 24시간 초과면 미상(null) + 백그라운드 재조회.
3. **위시 partial 캐시 쓰기 가드 (`wishForCache`)**: 위시 메타가 아직 다 오지 않았으면 일부 위시로 만든 목록 대신 이전 분석의 완전한 위시 결과를
   저장한다(이전 결과가 없으면 지금 목록). 메타 조회 순서 변경(`orderMetaFetch`)으로 미캐시 위시가 phase B로 밀린 데 따른 리뷰 지적 반영.
4. 주기 재블렌딩의 리뷰 조회(appreviews)는 phase B 메타 조회(store)와 동시에 돌 수 있다 — 서로 다른 한도라 의도한 동작. phase B가 끝나면
   진행 중 재블렌딩을 기다린 뒤 결과는 버리고 최종 단계가 전체로 다시 계산한다.
5. 3-2 대안 (b)는 채택하지 않음(3-1 구현).
