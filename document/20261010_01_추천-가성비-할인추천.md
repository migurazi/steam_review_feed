## 배경 및 목적

현재 `/recommend`는 "내 취향에 맞는 게임"만 고른다. 위시리스트 트랙조차 취향 매칭(0.65)
+ 리뷰 호평률(0.35)로만 정렬되어, **지금 할인 중이라 사기 좋은 게임**인지는 반영되지 않는다.
사용자가 원하는 것은 "취향에 맞고, 평이 좋고, 지금 싸게 살 수 있는 게임"이다.

두 단계로 나눈다. 비용·리스크가 크게 다르기 때문이다.

| 단계 | 범위 | 추가 비용 | 리스크 |
|------|------|-----------|--------|
| 1 | 위시리스트 트랙에 가격 배지 + 할인 매력도 블렌딩 + "할인 중만" 필터 | 가격 배치 조회 수 회 | 낮음 (기존 데이터 재사용) |
| 2 | 미보유·위시리스트 밖 **할인 게임 발굴** 트랙 신설 (opt-in) | 후보 수집 수 회 + 메타 ≤40회 + 리뷰 ≤30회 | 중간 (비공식 엔드포인트 의존) |

**비목표**
- "플레이 시간당 가격" 지표 — 게임 분량 데이터가 없어 정확도를 보장할 수 없음.
- 지역(통화) 선택 — 기존대로 `cc=KR` 고정.
- 리뷰 피드(`/api/reviews/stream`)의 LRU 묵은 가격 문제 — 아래 "현재 상태"에 기록만 하고
  본 작업에서 고치지 않는다(후속 작업 후보). 본 작업은 피드 동작을 바꾸지 않는다.

## 현재 상태

### 추천 파이프라인 (`app/api/recommend/route.ts`)
1. 라이브러리 + 위시리스트 fetch → 4-bucket 순서로 `getAppDetailsBatch`(`lib/steam/api.ts:572`, 1.5s 직렬).
2. `computeRecommendations`(`route.ts:205`) → 트랙별 매칭 shortlist(`min(max·2, 30)`, `route.ts:559-563`).
3. shortlist에만 `getReviewSummary`(0.5s 직렬) → `blendRecommendations`
   (`W_MATCH=0.65`, `W_REVIEW=0.35`, `lib/steam/profile.ts:401-402`) → 배지 부착.
4. partial-result는 match-only(3초 throttle), final result만 블렌딩. 결과는
   `recommendation_cache`에 **사용자당 1행**(`ON CONFLICT(user_id)`) 영속화,
   다음 방문 시 `cached` 이벤트로 즉시 표시.

### 가격 데이터 가용성 — 현 구조로는 신선한 가격을 보장할 수 없음
`getAppDetails`(`lib/steam/api.ts:327-401`)의 세 경로에서 `price_overview` 상태가 다르다.

| 경로 | price_overview |
|------|----------------|
| ① 인메모리 LRU 히트 (`app:{id}:info:KR`, TTL 7일, `api.ts:332-333`) | 있음. 단 **최대 7일 묵은 가격** |
| ② SQLite 영속 캐시 hydrate (`api.ts:341-347`) | **없음** (저장 시 stripping, `:388-393`) |
| ③ API 신규 조회 | 신선 |

추가로 LRU는 `allowStale: true`(`lib/cache.ts:26`)라 **TTL 만료 항목도 `cacheGet`이 반환**하고
`isStale=true`만 표시한다(`lib/cache.ts:81-92`). 따라서:
- `getAppPrice`(`api.ts:409-418`)는 `isStale`을 무시하고 만료 가격을 그대로 반환한다.
- 가격 캐시가 LRU에서 밀려난 경우에도 `getAppDetails`로 fallback하는데 이 함수는 ①/②를
  먼저 반환하므로 **실제 재조회가 일어나지 않는다**.
- 리뷰 피드(`app/api/reviews/stream/route.ts:81, 164, 296, 324`)는 info LRU의 `price_overview`를
  직접 읽는다(라이브러리 게임은 "캐시만 사용", `:321-322`). 즉 피드는 ①의 묵은 가격에 의존 중.

→ 추천은 `detailsMap`의 `price_overview`를 **절대 쓰지 않고**, 가격 전용 조회 경로를 신설한다.
info LRU에서 가격을 지우는 방식은 피드 가격을 없애는 회귀를 만들므로 채택하지 않는다.

## 단계 1 — 위시리스트 가성비

### 1-1. 가격 전용 조회 (`lib/steam/api.ts`)

**신규 `getAppPricesBatch(appIds, onProgress?, isCancelled?): Promise<Map<number, PriceSnapshot>>`**

```ts
/** 추천용 가격 스냅샷. Map에 없는 appid = 가격 미상(조회 실패). */
interface PriceSnapshot {
  price: SteamPriceOverview | null; // null = 확인됨: 무료/미판매/지역제한
  fetchedAt: number;                // Unix ms
}
```

- **캐시 확인**: `app:{id}:price:KR`(기존 키·형식 `SteamPriceOverview | null`, TTL `appPrice`).
  `cacheGet` 결과가 **`isStale === true`면 미스로 취급**(C1). fresh 히트만 결과에 넣고
  `fetchedAt`은 `CacheEntry.fetchedAt`.
- **1-A (V1 통과)**: 미스분을 `PRICE_BATCH_SIZE`(V1 결과, 기본 50)씩
  `appdetails?appids=...&filters=price_overview&cc=KR`로 조회. 배치 전 `STEAM_API_DELAY.appDetails`
  + `appDetailsBackoffDelay()`. 배치마다 `isCancelled()` 확인.
- **1-B (V1 실패)**: 미스분을 appid별 단건 `filters=price_overview`로 조회(같은 delay/backoff).
- 응답 정규화: `success=true` + `data.price_overview` → 그 값. `success=true` + 가격 없음
  (`data: []` 등) → `price: null`. `success=false` → `price: null`.
- **fetch 실패(null/네트워크/429)**: 해당 appid는 **캐시에 쓰지 않고 Map에서 누락**(=미상).
  실패를 null로 캐시하면 1시간 동안 "무료/미판매"로 오표시된다.
- 성공분은 기존 키로 `cacheSet(..., CACHE_TTL.appPrice)`. **영속 저장 안 함**.

**`getAppPrice` 결함 수정** (`api.ts:409-418`): 가격 캐시가 fresh면 반환, stale/미스면
`getAppPricesBatch([appId])`를 호출하고 그 결과의 `price`를 반환(미상이면 stale 값이 있으면
stale 값, 없으면 null — 기존의 "장애 시 묵은 데이터라도 표시" 정책 유지). `/api/game/[appId]/price`
반환 형식 불변.
- **읽기 순서 주의 (N2)**: lru-cache v11은 `allowStale` 항목을 처음 `get`할 때 반환과 동시에
  삭제한다. `getAppPrice`는 **첫 `cacheGet` 결과(stale 값)를 지역 변수에 보관한 뒤** 재조회해야
  한다(재조회 후 다시 읽으면 없음). 같은 이유로 stale fallback은 만료당 1회만 가능 — 수용.
  `getAppPricesBatch`도 같은 첫 읽기에서 fresh/stale을 판정한다.

**`getAppDetails`는 변경하지 않는다.** 단, ③ 신규 조회 시 이미 하던 `app:{id}:price:KR` 저장은
유지(가격 캐시가 덤으로 채워짐).

**backoff 범위 확대 (M7)**: `fetchJson`의 `isAppDetails` 판정(`api.ts:206`)을
"`store.steampowered.com` 호스트이면서 `/appreviews/`가 아닌 URL"로 넓혀, 가격 배치·검색·
featuredcategories의 429도 공유 backoff를 올리게 한다. 함수명을 `isStoreRateLimited` 등으로
바꾸고 기존 appdetails 동작은 불변임을 테스트로 고정. (본 문서의 "store 레인"은 이 공유
backoff + 호출부별 고정 delay를 뜻한다 — 전역 직렬 큐는 신설하지 않는다.)

### 1-2. 가성비 점수 (`lib/steam/profile.ts`, 순수 함수)

가격 표현은 Steam 원형 `SteamPriceOverview`를 그대로 쓴다(별도 camelCase 복제 타입 없음, L1/L2).

```ts
/** 금액을 원(₩) 단위로 정규화. V5 결과에 따라 /100 여부 결정. KRW 외 통화는 null. */
export function priceToWon(p: SteamPriceOverview, amount: number): number | null

/** 할인 매력도 [0,1]. 할인 없음/가격 미상/null(무료·미판매) → 0. */
export function computeDealScore(price: SteamPriceOverview | null | undefined): number
```

산식 (r2, C3·M6 반영):
```
d = clamp01(discount_percent / 100)               // 할인 없으면 0 → dealScore 0
cheap = (KRW && finalWon 유효)
          ? 1 − min(finalWon, DEAL_PRICE_REF_KRW) / DEAL_PRICE_REF_KRW
          : 0
dealScore = d · (DEAL_BASE + (1 − DEAL_BASE) · cheap)      // DEAL_BASE = 0.75
```
- 할인율이 **곱 인자**이므로 할인 없으면 0, 소폭 할인은 가격이 아무리 싸도 작다.
  예: ₩1,000 10% → 0.1·(0.75+0.25·0.98)≈0.10 / ₩60,000 50%(final ₩30,000) → 0.5·0.875=0.44.
- 100% 할인: d=1, finalWon=0 → cheap=1 → **dealScore=1.0** (guard는 `finalWon < 0`·NaN만 0 처리).
- 범위: d∈[0,1], 괄호∈[0.75,1] → dealScore∈[0,1].
- 상수: `DEAL_BASE=0.75`, `DEAL_PRICE_REF_KRW=60000`(원 단위, V5 정규화 후 비교).

**블렌딩** — `blendRecommendations(shortlist, reviewScoreByAppid, limit, dealScoreByAppid?)`:
```
dealScoreByAppid 미전달:  score = 0.65·match + 0.35·review                    (기존, 비트 동일)
dealScoreByAppid 전달:    score = 0.45·match + 0.30·review + 0.25·deal
```
- 상수 `W_MATCH_V=0.45`, `W_REVIEW_V=0.30`, `W_DEAL=0.25` (합 1).
- 미전달 경로는 코드상 기존 식을 그대로 타게 분기(부동소수 재배열 금지)해 회귀 0 보장.
- dealScoreByAppid에 없는 appid(가격 미상) → deal=0 (가격 미상은 "할인 없음"과 같은 순위
  패널티를 받는다 — 문서화된 의도. 단 표시는 "할인 없음"이 아니라 미표시).
- 결과 Recommendation에 `dealScore?: number`.

**Recommendation 확장**
```ts
/** 가격 스냅샷. undefined = 미조회/미상, null = 확인된 무료/미판매. */
price?: SteamPriceOverview | null;
priceFetchedAt?: number;
dealScore?: number;
source: "library-unplayed" | "wishlist" | "store-deal";   // store-deal은 단계 2
```

**1-A 흐름 (V1 통과)** — 메타 조회 완료 후, shortlist 산출 전:
1. 위시리스트 전체 appid(소유 중인 위시 게임 포함 — 위시 트랙이 소유 여부와 무관하게 전체를 후보로 보므로. 구현 시 `wishlistIdsOnly`에서 변경)에 `getAppPricesBatch` → `priceMap`. SSE
   `progress { phase: "fetching-prices", loaded, total }`. 위시 300개 ≈ 6회 호출.
2. `priceCoverage = priceMap.size / wishlistIdsOnly.length`.
   `priceFetchFailed = priceCoverage < 0.5` (M3·M4).
3. `computeRecommendations(..., priceMap)` → `buildWishlistAnalyzedGame(item, details, snapshot)`이
   `price/priceFetchedAt`을 싣고, `recommendFromWishlist`가:
   - `saleOnly`면 `!(price?.discount_percent > 0)` 후보 제외(미상도 제외).
   - 매칭 shortlist(기존, matchScore 순) 산출.
4. **할인 후보 보강 (M5, N4)**: `valueWeighting && !priceFetchFailed`면, 매칭>0이면서 할인 중인 위시
   후보를 `computeDealScore(r.price)` 내림차순으로 최대 `maxRecommendationsPerTrack`개 골라 shortlist에 합집합
   (appid dedupe, 결정론: dealScore desc → appid asc). 리뷰 조회 대상이 최대 `30 + max`로 늘 수
   있음 — 상한 `REVIEW_SHORTLIST_CAP + maxRecommendationsPerTrack`으로 명시.
   순수 함수 `augmentWithDeals(shortlist, candidates, k)`로 `profile.ts`에 둔다.
   `candidates`의 출처: `recommendFromWishlist`는 `limit`로 truncate하므로(`profile.ts:688`),
   `computeRecommendations`가 위시 트랙에 대해 **truncate 전 전체 매칭 목록**(`wishlistAll`)도
   함께 반환하도록 확장한다(내부에서 `recommendFromWishlist(..., Number.MAX_SAFE_INTEGER)` 1회 후
   slice — 같은 정렬을 두 번 하지 않음).
5. 리뷰 블렌딩: 위시 트랙은 `valueWeighting && !priceFetchFailed`일 때만 `dealScoreByAppid` 전달.
   그 외(옵션 off 또는 가격 조회 실패)는 기존 산식 — **가격 실패가 조용히 순위를 바꾸지 않는다**.
6. `done`에 `priceFetchFailed: boolean` 추가.

**1-B 흐름 (V1 실패, M2, N3)**:
0. `computeRecommendations`는 `priceMap` 없이, **`saleOnly` 필터를 끈 상태**로 호출한다
   (가격이 없는 상태에서 1-A의 "미상 제외" 규칙을 적용하면 전부 탈락).
1. 기존대로 매칭 shortlist(≤30) 산출 → shortlist appid만 `getAppPricesBatch`(단건, 최대 30 × 1.5s
   ≈ 45초 추가, 2회차부터 1시간 캐시).
2. `saleOnly`는 **shortlist 후 필터 → truncate** (결과 수가 max보다 적을 수 있음). UI 토글 설명에
   "상위 후보 중"을 표기.
3. 할인 후보 보강(4)은 생략(전체 위시 가격을 모르므로). `priceCoverage`는 shortlist 기준
   (`priceMap.size / shortlist.length`)으로 계산.
4. 나머지(5·6)는 1-A와 동일.

**partial-result (M1, L5)**:
- partial은 가격 조회 전이므로 deal 없이 match-only(기존).
- `saleOnly`일 때 partial의 `wishlist`는 `null`로 보낸다. 클라이언트는 **`null`이면 기존
  위시리스트 state를 유지**(cached 결과가 있으면 그것, 없으면 "가격 확인 중" 플레이스홀더).
- 타입: SSE payload·`ResultData.wishlist`를 `Recommendation[] | null`로, `computeResultSignature`가
  `null`을 `"-"`로 직렬화.
- `saleOnly` partial의 캐시 write는 skip한다. 그 결과 saleOnly 분석 도중 탭을 닫으면 라이브러리
  트랙 partial도 저장되지 않는다 — **수용**(final write가 곧 덮고, saleOnly는 보조 뷰).

**signature**: `computeResultSignature`에 위시 항목별 `discount_percent` 포함 — 할인만 변해도
final write dedupe에 막히지 않게(현재 final은 force=true라 영향 없으나 partial 일관성).

### 2-4. 라우트 흐름

```

 discovering        getStoreSpecials(150)         실패 → storeDealsFailed
                    filterDiscoverPool
```

  backoff)는 끝까지 기다린다.
  - 리뷰 조회는 세 트랙 합류 dedupe이므로, store-deal 전용 appid만 별도 루프로 분리해
    `stopDiscover`를 적용한다(lib/wish 리뷰는 예산 영향 없음).
- 실패 격리: 2단계 어느 지점의 예외도 catch → `storeDeals=[]`, `done.storeDealsFailed=true`.
  lib/wish 결과는 정상 전송.
- 취소: 각 단계 시작 전·배치마다 `isCancelled()`(기존 패턴).

## 제약 조건

- **하위 호환**: `valueWeighting=false`(또는 가격 조회 실패)이면 위시 순위가 현재와 동일(회귀 테스트).
  라이브러리 트랙 불변. 리뷰 피드·게임 상세 가격 표시 불변. 구 캐시 row는 1회 miss, payload는
  optional 필드로 호환. `deal` 미사용 시 tracks 해시 형식 불변.
- **Rate Limit**: store 호스트 호출은 모두 `appDetails` delay + 공유 backoff. 직렬 유지, 신규
  동시성 금지. 발굴 트랙은 메타 40·리뷰 30·시간 120초 상한.
- **리뷰 조회 최악치 (N8)**: 라이브러리 30 + 위시 (30 + 보강 max≤30) + 발굴 30 = **최대 120회
  × 0.5s ≈ 60초**(캐시 전무 시, 현재 최대 60회 ≈ 30초에서 증가). `reviewSummary` 캐시 6시간으로
  2회차부터 대부분 히트. 보강은 `valueWeighting` on일 때만, 발굴은 opt-in일 때만 발생.

### 지시서와 달라진 점
1. **`getAppPrice`는 stale-while-revalidate.** stale이면 stale 값을 즉시 반환하고 백그라운드에서
   재조회한다(지시서는 재조회를 기다린 뒤 반환). 게임 상세 응답이 store delay(1.5s)+backoff(최대 30s)에
   묶이지 않게 하기 위함. 미스일 때만 재조회를 기다린다.
2. **`success=false`는 판매 불가(null)로 짧은 TTL(10분) 캐시.** 지역제한·삭제 앱이 매번 "미상"이 되어

3. **배치 재조회 실패 시 stale fallback은 24시간 이내 가격만** (`PRICE_STALE_FALLBACK_MAX_AGE_MS`),

4. **가격 조회 대상은 위시리스트 전체(소유 중인 위시 게임 포함).** 1-4 흐름 1의 주석대로 반영.
5. **`saleOnly` + 가격 조회 실패**: 위시 트랙을 비우고(일부 가격만으로 거른 결과는 오해 소지) 안내 문구를

   phase A 직후 위시 가격·리뷰 조회 전에 잠정 결과를 한 번 보내 라이브러리 트랙이 바로 보이게 했다.

1. **GetItems 도입 (부록 B 설계 확정 4 반영).** 발굴 pool의 가격·리뷰 요약·카테고리를 GetItems 2회로 처리한다.
   store-deal 후보의 appreviews 개별 조회와 pool 가격 배치(`getAppPricesBatch`)는 쓰지 않는다. 장르 메타만 appdetails(상한 40).
2. **SSE 순서**: 지시서는 `result`에 `storeDeals`를 싣는 설계였으나, 발굴(최대 120초)이 라이브러리·위시 표시를 늦추지 않도록
   `result`(lib/wish) → 발굴 → **`store-deals { storeDeals, failed, truncated }`** → `done` 순으로 보낸다. `result`에는 storeDeals가 없다.
3. **캐시 쓰기 2회**: result 직후(이전 분석의 storeDeals를 이어 씀) + 발굴 후. 발굴 실패, 또는 일부만 확인했는데 0건인 결과는 저장하지 않는다
   (캐시에는 실패 플래그가 없어 다음 방문에 "없음"으로 보이므로).
4. **GetItems categories를 사전 필터로 쓰지 않음.** 매칭은 장르만으로도 성립하는데 GetItems에는 장르가 없어, 카테고리 불일치로 거르면
   장르 매칭 후보를 잘못 버린다. 메타 대상은 "할인 중 + 리뷰 ≥ 10 + dealScore 상위 40"으로 고른다(리뷰 하한 M9를 메타 조회 전에 적용).
5. **실패/일부 확인 판정 (정직성)**: `failed` = 후보 수집 실패, GetItems 전량 실패, 장르 메타 전량 실패, 위시리스트 조회 실패(위시 게임을
   제외할 수 없음). `truncated` = 예산 초과로 건너뜀, 후보 소스 degraded(featured fallback·후속 페이지 실패), GetItems·메타 성공률 50% 미만.
6. 검색 첫 페이지가 success인데 `total_count>0`이고 행을 못 뽑으면 마크업 변경으로 보고 fallback + 로그. 빈 후보 목록은 캐시하지 않는다.
7. **isFree는 appdetails 기준.** GetItems `is_free`는 100% 할인 배포에도 true라(실응답 확인) 섞으면 기본 옵션 "무료 게임 제외"가
   가장 좋은 할인을 걸러 버린다.
8. GetItems에서 `price_cannot_be_displayed_as_discount`·`hide_discount_pct_for_compliance`가 켜졌거나 정가가 없는 옵션은 할인 0으로 본다.
9. GetItems 단계 progress phase는 지시서대로 `fetching-prices`를 재사용 (라벨 "가격 확인 중").
10. 끝난 할인이 담긴 캐시 카드(`discountEndsAt` 경과)는 종료 문구만 숨기고 회색 가격으로 표시 — 위시 트랙과 같은 정책(미반영).
11. 이전 발굴 결과 이어 쓰기: 중간 캐시 쓰기는 이전 storeDeals를 현재 라이브러리·위시리스트로 다시 걸러 이어 쓴다(위시리스트 조회
    실패 시 이어 쓰지 않음). 발굴 실패 시 store-deals 이벤트의 `previous`로 거른 이전 결과를 보낸다.
    - `cached` 이벤트는 라이브러리 조회 전에 나가므로, 조회 직후 걸러서 빠진 게임이 있으면 **`cached-store-deals { storeDeals }`**로
      교체본을 보낸다 (/code-review #7). 그 사이(라이브러리 조회 시간, 보통 1초 내외) 거르기 전 목록이 보일 수 있다.
    - 이번 발굴이 저장할 수 없는 결과(실패, 일부 확인 + 0건)면 result 직후 이어 쓴 묵은 목록을 빼고 다시 쓴다 (/code-review #8).
    - 알려진 한계: 이어 쓴 목록도 final 쓰기의 새 `computed_at`을 받아 캐시 배너의 "N분 전"이 발굴 결과 기준으로는 실제보다 새것처럼
      보인다(가격은 `priceFetchedAt`으로 회색 구분).
12. 검색 후속 페이지가 `start < total_count`인데 0행이면 끝이 아니라 이상으로 보고 degraded·미캐시 (/code-review #4).
